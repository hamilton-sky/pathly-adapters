## Findings and where they went

1. **The chief inherits the user's and project's allow rules.** Allow rules from every loaded
   settings file merge, so `Bash(python3 *)` or `WebFetch` in the user's settings would let the
   chief call the server without its token (anonymous, unrestricted on loopback until RRP-2b).
   Applied: ticket 06 starts claude with `--restricted` (or `--setting-sources` with no sources)
   and `--tools Bash,Read,Glob,Grep`, and denies `WebFetch` and `WebSearch`; spec § Decisions,
   "The chief's claude permissions".
2. **A server-chosen `--session-id`.** Applied: tickets 05 (`cli_session_id`), 06 and 09 (hook
   posts from another session id are refused). Correction to the first version of this finding:
   it was offered as closing the cross-session open question, and it does not. A message another
   claude session sends into the chief arrives in the chief's own process with the chief's
   session id, so the check binds the process, not the typist. Ticket 09 now measures whether such
   messages can be told apart and labelled `relayed` (never citable); map.md § Open questions keeps
   the rest.
3. **Pathly relays the cited text; the chief does not retype it.** The word-for-word rule would
   refuse honest answers whenever shell quoting of the JSON argument to `pathly api` slips.
   Applied: ticket 10 (the chief sends only `cite`; the routes read the answer through
   `chief_cite.answer_text`), ticket 13 scenario 4, spec § Decisions, "What a citation proves".
4. **Round two's billing plan could not work.** An interactive claude tab prints no JSON cost
   summary, and restricted mode does not load the user's stop hook. Applied: map.md § Round two,
   item 8 reads the claude transcript that `cli_session_id` locates.
5. **The chief's prompt skipped fragments.** Applied: ticket 17 adds a `chief-connect` fragment,
   appended to every style, which carries the fixed rules (cite only, orders only from the user in
   the tab) so a saved style cannot drop them; spec § Decisions, "The chief's fixed rules".
6. **Daycap tickets.** Ticket 19 (guard spike) stays: no code, no blockers. It now notes that the
   chief tab does not run daycap's guard (restricted mode) and that a guard denying tool calls does
   not stop token spend. Ticket 18 (spend report) moved to `round-two-drafts/daycap-spend-report.md`:
   it is a reporting surface ticket 13 does not cover, and it proposed a `billing/` package outside
   the layer rule, a route in no existing blueprint domain, and a second program in the chief's
   allow list. Its corrections are at the top of the draft.
