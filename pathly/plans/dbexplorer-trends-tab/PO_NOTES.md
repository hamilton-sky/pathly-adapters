# PO Notes — dbexplorer-trends-tab
_Generated by PO advisor (autoFlow — best-guess, non-interactive)_

## Problem & Users

Studio's DBExplorer shows per-invocation cost and event-type breakdowns (AgentsTab,
InspectTab), but every view is point-in-time: there is no way to see how a feature's
cost, cache efficiency, or activity moved **over time**. A maintainer auditing a
feature's pipeline run cannot tell whether cost is trending up, whether the cache is
actually being hit, or how work was distributed across days without manually scanning
the raw events table.

**Primary user:** the Pathly developer/maintainer inspecting a single feature's run
history inside the DBExplorer FeatureModal (the same person who opens Agents/Inspect today).
**Secondary user:** anyone exporting a feature's agent run data for offline analysis
(spreadsheet, billing reconciliation, sharing).

## MVP Scope

A new **"Trends"** tab inside the existing `FeatureModal`, scoped to the **currently
open feature only** (the `feature.name` the modal was opened with). The tab renders four
sections, top to bottom:

### 1. Daily cost — bar chart
- **Shows:** total cost in USD per calendar day, one bar per day, for this feature's
  agent invocations. X-axis = day (`YYYY-MM-DD` or short `MMM DD`), Y-axis = cost USD.
- **Data needed per day:** summed `cost_usd`. When a row's `cost_usd` is `0`/null,
  fall back to the existing `computeCost(model, input_tokens, output_tokens, pricingTable)`
  estimate (reuse `costUtils.ts` — do not reinvent pricing). Mark days whose total
  includes any estimated value so the chart can distinguish reported vs estimated cost
  (badge/legend/color), consistent with how AgentsTab/InspectTab already label cost source.
- **Empty/zero days:** include calendar days with zero cost between the first and last
  active day so gaps in activity are visible (no "compressed" timeline that hides idle days).
- Recharts `<BarChart>`.

### 2. Cache efficiency — line chart
- **Shows:** cache hit rate over time, one point **per agent invocation** (chronological
  by `ts`), so the user can see cache warming/cooling across the run.
- **Metric:** `cache_read_tokens / (cache_read_tokens + input_tokens)`, expressed as a
  percentage 0–100. When the denominator is `0`, the point is undefined — render a gap,
  not `0%` (a false "0% cache" reading is misleading and was the kind of thing the user
  would challenge).
- X-axis = invocation order or `ts`; Y-axis = hit rate %. Recharts `<LineChart>`.
- A summary stat (overall feature cache hit rate across all invocations) above the chart
  is in scope and cheap; it gives the headline number without reading the line.

### 3. Activity heatmap — 18-week GitHub-style grid
- **Shows:** a fixed **18 columns × 7 rows** grid (126 day-cells), GitHub-contributions
  style, ending on the current week. Each cell = one calendar day, colored by the **number
  of agent runs** (count of `AGENT_DONE` / `agent_invocations` rows) that day for this feature.
- **Color buckets:** discrete intensity buckets (e.g. 0 / 1–2 / 3–5 / 6–9 / 10+) driven
  by `data-level` attributes per the CSS variant rule — no inline color styles. Days with
  zero runs render as the empty/baseline cell.
- **Window:** trailing ~18 weeks regardless of when the feature ran; days outside the
  feature's activity simply show as empty cells. Cells should expose the date + run count
  for hover/`title` (accessibility).

### 4. CSV export — single button
- **Shows:** one button (placed in the Trends tab, near the heatmap or as a tab-level
  action) that exports **all AGENT_DONE / `agent_invocations` rows for this feature** as a
  downloadable `.csv` file named after the feature (e.g. `<feature>-agent-runs.csv`).
- **Columns (one row per invocation):** `ts`, `agent`, `model`, `provider`,
  `input_tokens`, `output_tokens`, `total_tokens`, `cache_read_tokens`,
  `cache_write_tokens`, `cost_usd`, `cost_source`, `wall_seconds`, `feature`.
- **Mechanism:** client-side `Blob` + object-URL download, mirroring the existing
  `exportJson` pattern already in `FeatureModal.tsx` — no new IPC, no native save dialog
  required for MVP.

### Backend
- A new endpoint **`GET /telemetry/trends?feature=<name>`** on the FSM HTTP server
  (`http_server/blueprints/telemetry.py`) returns the daily aggregates the bar chart and
  heatmap need, queried from `~/.pathly/pathly.db` table `agent_invocations` filtered by
  `feature`. Minimum payload: per-day `{ date, run_count, cost_usd_reported, cost_usd_estimated_flag, input_tokens, cache_read_tokens }` (or enough to compute the four views).
- Cache-efficiency points and the CSV may be derived on the client from the events the
  modal already loads (`window.pathly.db.events(feature.name)` → `AGENT_DONE` payloads),
  OR included in the same `/telemetry/trends` response — implementation's choice, but the
  PO requirement is: **the four views must be consistent with the cost numbers already
  shown in AgentsTab for the same feature** (same fallback pricing, same source labeling).

### Wiring
- Add `'trends'` to the `TabId` union and the `tabs` array in `FeatureModal.tsx`, with an
  optional count = number of active days (or omit the count).
- New files only: `DBExplorer/TrendsTab/TrendsTab.tsx` + `TrendsTab.module.css`
  (plus sub-components/hooks as needed to respect the ~150-line / one-job component rule).

## Out of Scope

- **Global / cross-feature dashboard.** Trends is per-feature only. No "all features"
  rollup, no comparison between features.
- **Date-range pickers, zoom, or custom windows.** Bar chart spans the feature's active
  range; heatmap is a fixed trailing 18 weeks. No user-adjustable ranges in MVP.
- **Drill-down / click-through** from a bar, point, or heatmap cell into the underlying
  invocations (nice later; not MVP).
- **New chart types** beyond the three specified (no token-volume chart, no per-agent
  stacked breakdown, no wall-time chart) unless they fall out for free.
- **Server-side CSV generation / file picker / streaming export.** Client-side Blob
  download only.
- **Real-time / live-updating charts.** Data refreshes on the existing modal Refresh
  action; no polling or SSE for Trends.
- **Editing or backfilling telemetry data.** Read-only views.
- **Currency conversion, budgets, or alerting** on cost.

## Success Criteria

- Opening the Trends tab for a feature that has agent runs renders all four sections with
  real data from `~/.pathly/pathly.db`, no console errors, no inline styles (passes the
  repo's no-inline-style rule).
- Daily-cost bars **sum to the same feature total** already shown in the modal header /
  AgentsTab (same pricing + fallback), and visibly distinguish reported vs estimated cost.
- Cache-efficiency line shows a gap (not `0%`) for invocations with zero cacheable input,
  and the headline hit-rate matches a hand calc on the underlying rows.
- Heatmap renders exactly 18×7 cells, colors days by run count in discrete buckets, and
  shows date + count on hover.
- CSV export downloads a file whose row count equals the number of `AGENT_DONE` rows for
  the feature and whose columns match the spec above.
- A feature with **no agent runs** shows graceful empty states per section (the same
  "No AGENT_DONE events yet" tone used in AgentsTab) — never a crash or blank tab.
- `npm run typecheck` passes; `GET /telemetry/trends?feature=X` returns valid JSON for a
  known feature and an empty-but-valid shape for an unknown feature.

## Constraints

- **Tech stack (fixed):** React + TypeScript, **Recharts** (already a Studio dependency —
  do not add another charting lib), CSS modules, **no inline `style={{...}}`** except the
  documented CSS-custom-property exceptions. Colors/spacing from `tokens.css` variables.
- **Component rules:** ~150-line hard cap per file; one component = one job; per-component
  subfolder + `.module.css`; data fetching in a `useTrends`-style data hook, UI state in a
  separate hook if needed; every `<button>` has explicit `type="button"`.
- **Cost logic must reuse `DBExplorer/costUtils.ts`** (`computeCost`, `fetchPricingTable`,
  `PricingTable`) — no second pricing implementation. Pricing comes from
  `GET /telemetry/pricing` exactly as the other tabs consume it.
- **Backend layering:** the new endpoint lives in `http_server/blueprints/telemetry.py`
  and queries via `db/` query helpers; it must not bypass the established db-access layer.
- **Data source contract:** read-only against table `agent_invocations` (columns: `agent,
  model, total_tokens, cost_usd, wall_seconds, ts, cache_read_tokens, cache_write_tokens,
  input_tokens, output_tokens, feature, provider, cost_source`). Filter strictly by
  `feature` so the tab never leaks other features' data.
- **No new IPC channel** if the data can come from the existing
  `window.pathly.db.events()` path and the new HTTP endpoint via `fetch` (the pattern
  `costUtils.fetchPricingTable` already uses `fetch('http://127.0.0.1:8765/...')`).

## Edge Cases & Risks

- **Zero-input invocations → divide-by-zero** in cache rate. Must render a gap, not `0%`.
  (Product-level: a false "cache broken" signal would be actively misleading.)
- **`cost_usd = 0` rows** (provider didn't report) must fall back to estimate and be
  labeled as estimated, or the daily total will silently under-count — same trap the
  existing tabs already handle.
- **Sparse / single-day features:** bar chart and heatmap must look sane with one active
  day (don't render a single lonely bar with a broken axis; include surrounding empty days).
- **Timezone of `ts`:** "per day" bucketing must use a consistent timezone. Decide local
  vs UTC once and apply it identically in the bar chart, heatmap, and CSV so all three
  agree. (OPEN — see below.)
- **Feature with no runs / unknown feature name:** every section degrades to an empty
  state; the endpoint returns a valid empty shape, not a 404/500.
- **Long-running features older than 18 weeks:** heatmap is a *trailing* 18-week window,
  so early activity will fall off the grid by design — confirm that's acceptable (it is,
  for MVP; the bar chart still covers the full range).
- **Large invocation counts:** the per-invocation cache line could get dense for a feature
  with hundreds of runs; acceptable for MVP but watch chart readability.
- **DB locked / FSM server down:** `fetch` to `/telemetry/trends` can fail; the tab should
  show a non-fatal empty/error state, consistent with `fetchPricingTable` returning `null`.

## Open Questions

- OPEN: Day bucketing timezone — **local time vs UTC** for the bar chart and heatmap day
  boundaries (and the CSV `ts` formatting). Recommend local time to match what a developer
  sees, but this must be stated and applied uniformly. Defaulting to **local time** for the
  best-guess plan.
- OPEN: Should daily-cost split bars **by agent role** (stacked) or just show one total per
  day? Best-guess: **single total per day** for MVP (stacking is a follow-up).
- OPEN: Heatmap intensity bucket thresholds (run-count → color level). Best-guess buckets:
  `0 / 1–2 / 3–5 / 6–9 / 10+`; tune against real data.
- OPEN: Whether `/telemetry/trends` should also return the per-invocation cache series and
  the CSV rows, or whether the client derives those from `window.pathly.db.events()`.
  Best-guess: endpoint returns **daily aggregates**; client derives cache series + CSV from
  the events it already loads, to keep the endpoint small. Either is acceptable if the four
  views stay numerically consistent with AgentsTab.
- OPEN: Does the heatmap window end on **today** or on the feature's **last active day**?
  Best-guess: trailing 18 weeks ending **today** (GitHub-style), since the tab is "current
  state of this feature's activity."
