# PO Notes — stepper-pathly-ui
_Generated by PO advisor (autoFlow mode)_

## Problem & Users

Pathly Studio (Electron + React) has no automated UI regression coverage. Every change to HomeScreen, FlowEditor, Settings, or the chat/IPC contracts must be manually clicked through, which is slow and lets regressions land unnoticed. Meanwhile, the Playwright Stepper framework — already in use for web sites like openlibrary and saucedemo — has no Electron support, so it cannot reach Studio today.

**Primary user:** Yafit, developer on Pathly Studio, who needs repeatable UI smoke and regression flows to run locally before commits.

**Secondary users:** Future Pathly maintainers who will extend Studio panels and need a stable harness to add new UI tests without reinventing the launcher each time.

**No external/end users.** This is internal developer tooling.

## MVP Scope

The MVP delivers the smallest end-to-end loop: a Stepper workflow that launches the Electron app, picks a project, and navigates the main panels — proving the CDP plumbing and the POM/glue pattern work for Pathly Studio.

- **Electron CDP launcher** in `stepper/engine/`: browser context factory that spawns Electron with `--remote-debugging-port` and connects via `playwright.chromium.connect_over_cdp()`. Replaces the assumption that Stepper drives a stock browser.
- **`data-testid` attributes** on HomeScreen, Settings, and TopBar interactive elements (project picker, settings fields, panel switch buttons). Lowest-IPC-dependency screens first so the harness can be validated before touching FlowEditor/ChatPanel.
- **POMs** under `poms/pathly/pages/`: `HomeScreenPage`, `SettingsPage`, `TopBarPage`. Inherit the existing `SharedBasePage` pattern used by openlibrary/saucedemo.
- **Glue actions** under `stepper/sites/pathly/pages/` for the three POMs, plus `stepper/sites/pathly/register.py` to register the site with the Stepper engine.
- **Smoke workflow** at `stepper/sites/pathly/workflows/smoke.json`: launch app → select a project from HomeScreen → switch into each main panel via TopBar → assert each panel rendered → close.

## Out of Scope

Explicitly excluded from v1 to keep the surface area small:

- Full ChatPanel test automation (streaming LLM responses, async IPC, terminal output assertions).
- FlowEditor canvas interaction tests beyond "panel opens" (node drag, edge creation, zoom/pan).
- Visual regression / screenshot diffing.
- CI pipeline integration (GitHub Actions, headless Electron in CI). Local-only for v1.
- Performance tests, load tests, or timing assertions.
- Cross-platform launcher coverage beyond the developer's current OS (Windows). macOS/Linux launcher variants come later.
- Replacing or modifying existing openlibrary/saucedemo site configs.

## Success Criteria

Measurable outcomes that prove MVP works:

1. Running the smoke workflow from a clean checkout launches the Electron app, drives it through project selection and panel navigation, and exits cleanly — with no manual intervention.
2. The smoke workflow passes locally in under 60 seconds on the developer's machine.
3. Adding one new `data-testid` and one new POM method for a HomeScreen/Settings/TopBar element is documented and takes under 15 minutes for a new contributor.
4. The CDP launcher is reusable: a second Electron app (hypothetical) could be wired in by only changing the executable path and app-specific config — not the launcher core.
5. Zero regressions introduced into Studio runtime behavior by the `data-testid` additions (they are inert attributes, no logic change).

## Constraints

- **No plain-browser testing.** Studio's renderer depends on `window.pathly.*` IPC via contextBridge. Pointing Playwright at `localhost:5173` directly will fail — the harness must connect to the actual Electron renderer over CDP.
- **Stepper architecture must be respected.** Three-layer pattern (POM → Glue → Workflow JSON) is non-negotiable; the Pathly site must look like openlibrary/saucedemo structurally so future contributors recognize it.
- **Vite dev server lifecycle.** `npm run dev` starts both Vite and Electron; the launcher must either reuse a running dev session or be able to bring up the full stack and tear it down.
- **No data-testid attributes exist today** across the renderer, so MVP introduces the convention from scratch. Naming convention should be agreed before sprinkling them across screens.
- **Windows-first** for the developer's environment; PowerShell-friendly commands required.
- **Stepper is Python + Playwright; Studio is TypeScript + Electron.** Cross-language coordination — test changes and app changes live in different repos/dirs (`playwright-stepper-framework` and `pathly-adapters/studio`).

## Edge Cases & Risks

Product-level risks that could derail MVP or v2:

- **CDP launcher race conditions.** Electron may not have the renderer window ready when Playwright tries to connect. Need a readiness probe (e.g., wait for `window.pathly` to be defined on a known page) before workflow steps run.
- **Project picker state pollution.** HomeScreen lists recent projects from local config. Tests must either operate on a known fixture project or clean up after themselves so re-runs are deterministic.
- **Settings persistence.** SettingsPage writes to disk via IPC. Smoke tests must not mutate the developer's real Pathly config — needs a sandbox config dir or read-only assertions.
- **`data-testid` drift.** If Studio components are refactored (e.g., the recent `ConductorHeader → ChatHeader` rename) the test IDs can silently break. Need a convention that test IDs are treated as part of the component contract, not cosmetic.
- **Electron version coupling.** The CDP launcher is sensitive to Electron's Chromium version vs. Playwright's bundled Chromium. Upgrades to either may break the connection.
- **Dev vs. packaged app.** MVP targets `npm run dev`. A packaged production build has a different binary path and startup sequence — out of scope but flag for v2.
- **No fallback if CDP fails.** Because plain-browser testing is impossible, a broken launcher blocks 100% of tests. The launcher needs clear error messages pointing at the likely cause (port in use, Electron not built, etc.).
