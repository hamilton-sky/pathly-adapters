# PO Notes — brightsky-chat-connect
_Generated by PO advisor (autoFlow)_

## Problem & Users

**Problem:** Pathly Studio's chat panel currently only routes to local LLMs (Ollama, node-llama-cpp). Users who want to chat with Brightsky's hosted NestJS backend — which provides session management, persistent conversation history, and authenticated multi-device access — have no in-Studio path to do so. Today they must leave the app and use a separate client, breaking the Studio workflow and losing context.

**Primary users:** Pathly Studio developers/operators who already use Brightsky as their hosted chat backend and want a single desktop surface for both local and cloud models.

**Secondary users:** Studio users evaluating Brightsky as an alternative to local LLMs (faster models, cross-device sessions, server-side memory).

## MVP Scope

- Add **Brightsky** as a selectable option in the existing Studio `ModelSelector` (alongside Ollama / node-llama-cpp).
- **Google OAuth login** via `brightsky://` custom protocol registered in Electron main; auth code exchanged through `POST /auth/exchange-code`.
- **Token storage** in `electron-store` with automatic refresh before expiry.
- **WebSocket chat** opened directly from the renderer to `wss://[app].onrender.com/ws` (no IPC bridge — native browser WebSocket API).
- **Streaming** via `stream_chunk` events that reuse Studio's existing `updateLastMessage` streaming path.
- New **`brightskyStore.ts`** holding `{ connected, authenticated, sessionId, wsUrl, authUrl }`.
- **Session lifecycle**: `create_session_with_message` for the first turn, `user_message` for subsequent turns, leveraging the recently-built `ConductorHeader` sessions dropdown.
- **Connect / auth UI affordance**: auth dot indicator + "Connect" button in `ModelSelector` when Brightsky is selected but unauthenticated.

## Out of Scope

- Replacing or deprecating the local LLM backends (Ollama, node-llama-cpp remain primary defaults).
- Server-side changes to the Brightsky NestJS backend — this feature consumes the existing API surface as-is.
- Custom auth providers beyond Google OAuth (no email/password, no SSO, no enterprise IdP).
- Cross-session search, export, or bulk session management UI in Studio.
- Tool-calling / agent orchestration over the Brightsky transport (text streaming only for MVP).
- File / image attachment uploads through the WebSocket.
- Offline queueing or local cache of remote sessions.
- Multi-account switching within a single Studio install.

## Success Criteria (Acceptance)

1. **Selection works:** User can pick "Brightsky" in `ModelSelector` and the choice persists across Studio restarts.
2. **OAuth round-trip succeeds:** Clicking "Connect" opens the system browser to Google OAuth; the `brightsky://` callback is caught by Electron main, the code is exchanged via `POST /auth/exchange-code`, and the returned JWT is stored in `electron-store`.
3. **Auth indicator is accurate:** The auth dot in `ModelSelector` reflects `brightskyStore.authenticated` in real time (red/grey when logged out, green when authenticated with a valid token).
4. **WebSocket connects and streams:** Once authenticated, selecting Brightsky and sending a message opens `wss://[app].onrender.com/ws`, emits `create_session_with_message`, and renders `stream_chunk` events incrementally via `updateLastMessage` in the existing `ChatPanel`.
5. **Follow-up turns reuse the session:** Subsequent messages emit `user_message` with the active `sessionId` rather than creating a new session.
6. **Token auto-refresh:** When the JWT nears expiry, it refreshes silently without forcing the user to re-authenticate or interrupting an active chat.
7. **Sessions dropdown integration:** The existing `ConductorHeader` sessions dropdown lists Brightsky sessions for the authenticated user and switching sessions updates `brightskyStore.sessionId` correctly.
8. **Graceful failure modes:** Auth failures, WebSocket disconnects, and 401 token-expired responses surface a clear inline error in the chat panel and offer a one-click "Reconnect" action — Studio does not crash or silently drop messages.

## Constraints

- **Platform:** Electron app — must work on Windows, macOS, and Linux desktop builds.
- **Custom protocol:** `brightsky://` registration is a per-OS concern; macOS and Windows behave differently and must both be tested.
- **Renderer security:** WebSocket is opened from the renderer, so the JWT must be passed safely (handshake header or first-message auth payload — not embedded in URL query strings that may leak to logs).
- **No new IPC bridge for chat traffic** — only for OAuth code exchange and token storage. Chat streaming stays in the renderer.
- **Backend contract is fixed:** event names (`create_session_with_message`, `user_message`, `stream_chunk`) and the `/auth/exchange-code` endpoint are dictated by the existing Brightsky NestJS service and cannot be renegotiated in this feature.
- **Render hosting:** Brightsky runs on Render, which sleeps free-tier instances — first-message latency may be high and the UI should not interpret cold-start delay as a failure.
- **Token storage:** `electron-store` is plaintext on disk by default; tokens must be stored with OS-keychain encryption or `electron-store` encryption key, not as cleartext.
- **Existing streaming contract:** Must reuse `updateLastMessage` exactly as the local backends use it — no divergent streaming primitive.

## Edge Cases & Risks

- **OAuth callback lost:** If the user closes the browser tab before the `brightsky://` callback fires, the connect flow must time out cleanly and let the user retry.
- **Multiple Studio windows:** Only one window should claim the `brightsky://` callback; secondary windows must not race the auth exchange.
- **WebSocket drop mid-stream:** A disconnect during `stream_chunk` delivery should mark the in-flight assistant message as incomplete and offer retry, not leave a half-rendered bubble.
- **Token expires mid-conversation:** Refresh must happen transparently; if refresh fails, the user is logged out and prompted to reconnect rather than silently failing every send.
- **Backend cold start:** Render free-tier wake-up can take 30–60s; UI needs a "connecting…" state distinct from "failed."
- **Model selector confusion:** Users may not understand that "Brightsky" is a backend (not a model) — labeling should make clear that selecting Brightsky may further expose model choice via the backend.
- **Session ownership:** If the user logs out and back in as a different Google account, the local `sessionId` cache must be invalidated.
