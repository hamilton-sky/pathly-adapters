## Decisions Made

- **YAML owns what + when, orchestrator executes** — `transition_actions` key added to flow YAML; orchestrator becomes a pure FSM engine with zero knowledge of side-effect intent
- **Level 2 agnosticism (blind substitution)** — orchestrator merges `{**flow_params, **state_json}` into one flat context dict and calls `template.format(**context)`; no named variable list maintained
- **Wrapped substitution error** — on KeyError, orchestrator prints: transition name, unknown variable, and `list(context.keys())`; no load-time validation needed
- **Single `spawn` action type** — not `spawn_skill` vs `spawn_agent`; orchestrator dispatches by name, doesn't care what kind of thing the target is; transition actions are fire-and-forget (no FSM branching on result)
- **Fixed action vocabulary for now**: `git_commit`, `update_progress`, `archive_artifacts`, `spawn`
- **App owns the flow, YAML is a build artifact** — users never hand-edit YAML; app is the authoring surface
- **Package is single source of truth** — app reads skills/agents/action types FROM package; exports YAML + generated skill file BACK to package; `materialize_flows()` syncs to `~/.claude/` for Claude Desktop and Codex
- **Auto-discovery by command name** — `/pathly-{name}` maps to `flows/{name}.flow.yaml`; wrapper skill resolves the path (~20 lines)
- **Skill auto-generation on export** — app generates both `{name}.md` (skill logic) and `{name}_skill.yaml` (meta) from a boilerplate template; no hand-writing needed for new flows
- **Wizard UI for the app (not canvas)** — structured step-by-step form: name → states+agents → exit routing → side effects → validate+sync
- **Two-level validation before export** — ERRORS hard-block (no initial_state, transition to unknown state, agent missing); WARNINGS soft-block with "Fix first / Sync anyway" choice (state has no exit routing, no `->DONE` transition, no transition_actions)
- **Build sequence: FSM changes first, app second** — Phase 1: `fsm-transition-actions` (3 convs, already planned); Phase 2: discovery wrapper; Phase 3: wizard app

## Options Rejected

- **Level 1 agnosticism (named variable list)** — rejected because every new STATE.json field would require an orchestrator edit; defeats the purpose of the generic engine
- **Load-time validation of substitution variables** — rejected because STATE.json doesn't exist at load time; incomplete validation is worse than a clear runtime error
- **Two separate spawn types (`spawn_skill` vs `spawn_agent`)** — rejected because transition actions are fire-and-forget side effects; orchestrator doesn't branch on their result, so the distinction adds complexity with no benefit
- **Raw YAML editor as app MVP** — rejected because it defeats the purpose for non-technical users
- **Full visual canvas as app MVP** — rejected as too complex for v1; wizard is the right starting point
- **Flows at `~/.claude/flows/` (user-level, outside package)** — rejected in favour of package-as-source-of-truth so deploy stays the single sync mechanism

## Constraints

- Orchestrator must never contain hardcoded references to team-pipeline concepts (conv numbers, PROGRESS.md paths, artifact locations) — these belong in flow YAML
- New action types require a deliberate orchestrator.md edit (intentionally limited vocabulary prevents arbitrary shell execution from YAML)
- `transition_actions` is optional in schema — flows with no side effects must remain valid
- App-generated skill files must follow the existing stitch pipeline: core `.md` + `*_skill.yaml` meta file
- `materialize_flows()` already copies all `*.flow.yaml` — no changes needed to deploy mechanism for new flows

## Open Questions

- Should `required: true` be supported on a `spawn` transition action (blocks flow if target fails), or is fire-and-forget sufficient for all current use cases?
- Where does the wizard app live — standalone Electron/web app, or embedded in Claude Desktop as a plugin?
- Should the app support re-importing a YAML (round-trip editing), or is export strictly one-way?

## Context Summary

We stormed on `fsm-transition-actions` — moving hardcoded side effects (git commits, PROGRESS.md updates, artifact archiving) out of `orchestrator.md` and into flow YAMLs via a `transition_actions` key. The session expanded into a broader product vision: a visual wizard app that reads skills/agents from the pathly package, lets users design flows step-by-step, validates before export, and auto-syncs to Claude Desktop and Codex via the existing `materialize_flows()` deploy mechanism. The immediate build target remains the FSM changes (3 convs already planned); the wizard app is a follow-on feature.
