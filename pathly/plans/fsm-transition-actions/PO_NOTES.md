# PO Notes — fsm-transition-actions
_Generated by PO advisor (autoFlow mode)_

## Problem & Users
Orchestrator.md currently hardcodes side effects (git commits, PROGRESS.md updates, artifact archiving) for specific flows, making it impossible to add or modify flow behavior without editing orchestrator logic. Flow authors and Pathly maintainers need a declarative way to attach side effects to FSM transitions so the orchestrator stays a pure engine.

## MVP Scope

### Story 1: Declarative transition_actions in flow YAML
**As a** flow author,
**I want** to declare per-transition side effects in the flow YAML under a `transition_actions` key,
**so that** I can add or change flow behavior without touching orchestrator code.

**Acceptance criteria:**
- New `transition_actions` field added to flow YAML schema, keyed by `FROM->TO` transition strings.
- Action vocabulary supported: `git_commit`, `update_progress`, `archive_artifacts`.
- `team.flow.yaml`, `debug.flow.yaml`, and `explore.flow.yaml` updated to declare their existing side effects via this field.
- Field is optional — flows without side effects omit it entirely.

### Story 2: Orchestrator executes transition_actions generically
**As a** Pathly maintainer,
**I want** the orchestrator to read and execute `transition_actions` from the active flow YAML,
**so that** orchestrator.md becomes a pure FSM engine with no knowledge of any specific flow's side effects.

**Acceptance criteria:**
- All hardcoded git commit, PROGRESS.md update, and artifact archive logic is removed from orchestrator.md.
- Orchestrator looks up the current `FROM->TO` transition in `transition_actions` and executes any listed actions generically.
- Transitions with no declared actions execute cleanly (no-op).
- Existing flow behavior (team/debug/explore) is preserved end-to-end after the refactor.

### Story 3: Schema validation for transition_actions
**As a** flow author,
**I want** `state.py` / `validate_flow` to recognize and validate the `transition_actions` key,
**so that** typos in action names or transition keys are caught early instead of silently failing at runtime.

**Acceptance criteria:**
- `validate_flow` recognizes `transition_actions` as a known top-level key.
- Validator warns (does not error) if `transition_actions` is absent.
- Validator errors on unknown action names or malformed transition keys.
- `state.py` loads and exposes `transition_actions` for orchestrator consumption.

## Out of Scope
- New action types beyond `git_commit`, `update_progress`, `archive_artifacts`.
- Conditional or parameterized actions (e.g. action arguments, when-clauses).
- Async / parallel action execution.
- Action plugin system or user-defined actions.
- Migration tooling for third-party flow YAMLs.

## Success Criteria
- orchestrator.md contains zero flow-specific side effect logic after the change.
- All three existing flows (team, debug, explore) produce identical observable behavior before and after refactor.
- Adding a new side effect to an existing flow requires editing only one YAML file.
- `validate_flow` rejects malformed `transition_actions` blocks with a clear error message.

## Constraints
- Must preserve backward compatibility for flows that omit `transition_actions`.
- Three-conversation split is fixed (schema, orchestrator, validator).
- Action vocabulary is closed for this MVP — no extensibility hooks.

## Edge Cases & Risks
- A transition key references a `FROM->TO` pair that does not exist in the FSM — validator must catch this.
- An action listed for a transition fails mid-execution (e.g. git commit fails) — orchestrator behavior on partial failure must match current behavior.
- Flow YAML declares `transition_actions` but orchestrator runs against an older schema version — version mismatch handling.
- Removing hardcoded logic from orchestrator.md risks regressing flows whose YAMLs were not updated; the three known flows must all be migrated in lockstep.

## Open Questions
- OPEN: On action failure mid-transition, does the FSM abort the transition or proceed? (Assumed: match current orchestrator.md behavior — confirm during architect storm.)
- OPEN: Order of actions within a single transition — is it the YAML list order, and is it guaranteed sequential? (Assumed: YAML order, sequential.)
- OPEN: Should `transition_actions` support a wildcard `*->TO` or `FROM->*` key for catch-all side effects? (Assumed: no, explicit pairs only for MVP.)
