# PO Notes — editor-comment-system
_Generated by PO advisor_

## Problem & Users
Reviewers reading a markdown file in Pathly Studio's preview can today attach a comment to a text selection and send the batch to an agent, but every comment renders in one undifferentiated `pathly-submitted` highlight color and there is no way to tell, at a glance, which highlight maps to which comment card, jump between them, or visually find a comment's anchor on a long page. The user is a **developer reviewing skill/agent/template markdown** inside Studio's preview tab; the pain is loss of orientation once a file has more than two or three open comments.

This feature adds per-comment identity (an index badge and one of five colors), bidirectional navigation between the comment panel and the highlighted text, and margin gutter markers — turning a flat list into a navigable review surface.

## Existing system (grounding — do NOT re-implement)
- `useComments.ts` already owns the persisted model: `Comment = { id, lineNumber, lineText, body, resolved, createdAt }` persisted to a `*.comments.json` sidecar with a 400ms debounce. **`color` and `index` are new fields; `index` is derived, not persisted (see story 9).**
- `CommentablePreview.tsx` already captures a live `Range` (`pendingRangeRef`, `tooltipRangeRef`) at selection time and re-applies highlights in a `useEffect` keyed on `[pendingAnchor, modalOpen, content, submittedAnchors, showHighlights]`.
- `highlightUtils.ts` already exposes `findAnchorRange` (progressive text-search fallback), `applyHighlights`, `clearHighlights`, and the CSS Custom Highlight API plumbing (`pathly-pending`, `pathly-submitted`). **Submitted highlights are re-derived from the `lineText` string on every render via `findAnchorRange` — there is no persisted range.** This is the single most important fact driving the edge cases below.
- `CommentsPanel.tsx` already renders unresolved/resolved `CommentItem`s and a count `badge`, plus the highlight show/hide eye toggle.
- Studio rules: no inline styles (CSS modules only; CSS vars via `setProperty` in a `useEffect`), `type="button"` on every button, ARIA on interactives, ~150 lines/file hard limit.

## User Stories

### Story 1 — Per-comment color on creation
**As a** developer, **I want** to pick one of five preset colors when I create a comment, **so that** I can visually group or prioritize related comments.
**Acceptance criteria:**
- Color picker offers exactly 5 presets: yellow (default), green, blue, purple, orange.
- New comment with no explicit choice persists `color: "yellow"`.
- `color` is persisted into the `*.comments.json` sidecar as a new field on `Comment`.
- A pre-existing comment loaded from a sidecar that lacks `color` defaults to `yellow` at read time (back-compat — old sidecars must not break).

### Story 2 — Colored highlight in the preview
**As a** developer, **I want** each comment's anchor text highlighted in that comment's color, **so that** the panel card and the highlighted text are visually linked.
**Acceptance criteria:**
- Each unresolved comment renders a named CSS highlight `pathly-comment-{id}` carrying its own color.
- The legacy single `pathly-submitted` highlight is replaced by per-comment named highlights (no comment shows the old undifferentiated color).
- Resolved comments are not highlighted in the preview.
- When `showHighlights` is off, no per-comment highlights render (existing eye toggle still governs all).
- If the CSS Custom Highlight API is unavailable, the feature degrades silently (no highlights, no crash) — matching current `apiAvailable` guard.

### Story 3 — Index badge on each card and gutter
**As a** developer, **I want** each comment numbered (#1, #2, …), **so that** I can reference "comment 3" unambiguously while reviewing.
**Acceptance criteria:**
- `CommentCard` shows an index badge matching document order (top-to-bottom by `lineNumber`, the existing sort key).
- The badge index is contiguous (1..N) across **unresolved** comments; resolved comments do not consume an index (see story 9 for the ordering contract).
- The badge color matches the comment's color.

### Story 4 — Anchor text preview on the card
**As a** developer, **I want** each card to show the first ~50 chars of the anchored text, **so that** I know what the comment refers to without scrolling to it.
**Acceptance criteria:**
- Card displays `anchorText` truncated to 50 chars with an ellipsis when longer.
- Truncation is visual only; the full stored `lineText` (already capped at 120 chars upstream) is unchanged.
- Whitespace in the preview is collapsed to a single space for display.

### Story 5 — Click card to scroll + pulse
**As a** developer, **I want** clicking a comment card to scroll the preview to its anchor and pulse it, **so that** I can locate the referenced text instantly.
**Acceptance criteria:**
- `CommentablePreview` exposes an `onScrollToComment(id)` prop (or imperative handle) wired from the panel.
- Clicking a card scrolls the anchor into view (`scrollIntoView`, centered/nearest).
- A 300ms pulse highlight plays on the anchor on arrival, then clears automatically.
- If the anchor cannot be located (text deleted/changed), see Story 8 edge handling — no scroll, no crash.

### Story 6 — Comment count badge on the panel toggle
**As a** developer, **I want** the unresolved comment count visible on the panel toggle, **so that** I know there are open comments even when the panel context is collapsed.
**Acceptance criteria:**
- Count reflects **unresolved** comments only (consistent with the existing `unresolved.length` badge in the header).
- Badge hidden when count is 0.
- Reuses/extends the existing `styles.badge` rather than introducing a parallel styling path.

### Story 7 — Margin gutter badges
**As a** developer, **I want** small numbered markers (①②③) at the left edge of each highlighted span, **so that** I can scan the document margin and map regions to comments.
**Acceptance criteria:**
- A gutter marker renders aligned to the top of each comment's anchor `Range` (use `range.getBoundingClientRect()`, already used elsewhere in this component).
- Marker shows the same index and color as the card.
- Markers reposition on content change and on container scroll/resize (the highlight `useEffect` already re-runs on `content`; scroll/resize must also trigger reposition).
- Markers do not render for resolved comments or when `showHighlights` is off.
- Markers are positioned via CSS custom properties set with `setProperty` in a `useEffect` — **never** an inline `style={{}}` prop (Studio rule).

### Story 8 — Keyboard navigation between anchors
**As a** developer, **I want** Alt+↑ / Alt+↓ to jump between comment anchors while focused in the preview, **so that** I can review comments without the mouse.
**Acceptance criteria:**
- Alt+↓ moves to the next anchor in document order; Alt+↑ to the previous; both wrap at the ends.
- Each jump performs the same scroll + 300ms pulse as a card click (shared helper).
- The listener is scoped to the preview (added/removed on focus/mount), and does not collide with the existing global Ctrl/Cmd+S save handler.
- Navigation skips anchors that cannot currently be located, rather than getting stuck.

### Story 9 — Stable index ordering contract
**As a** developer, **I want** comment numbers to stay meaningful as I add, resolve, and delete, **so that** indices are predictable during a review.
**Acceptance criteria:**
- Index is **derived at render time** from the sorted unresolved list (by `lineNumber`), not persisted — adding/removing a comment renumbers consistently.
- Document order is the single source of truth (matches the existing `.sort((a,b) => a.lineNumber - b.lineNumber)`).
- Card, highlight target, and gutter marker for a given comment always show the same number within a render.

### Story 10 — Resolve still works with colors/indices
**As a** developer, **I want** resolving a comment to remove its highlight, gutter marker, and index, **so that** the review surface reflects only open items.
**Acceptance criteria:**
- Resolving clears that comment's `pathly-comment-{id}` highlight and gutter marker on the next render.
- Remaining unresolved comments renumber to stay contiguous (1..N).
- Resolved comments remain visible in the panel's "Resolved" section (existing behavior) but carry no preview presence.

## MVP Scope (ships in v1)
- New `color` field on `Comment` (persisted) + back-compat default to `yellow` on load.
- Derived `index` (render-time, not persisted) — Stories 3 & 9.
- 5-preset color picker at creation (Story 1).
- Per-comment named CSS highlights `pathly-comment-{id}` replacing the single `pathly-submitted` (Story 2).
- `CommentCard` with index badge, color, 50-char anchor preview, body, resolve button (Stories 3, 4, 10).
- Click-to-scroll + 300ms pulse via `onScrollToComment(id)` (Story 5).
- Unresolved count badge on panel toggle (Story 6) — extends existing badge.
- Margin gutter badges (Story 7).
- Alt+↑/↓ keyboard nav scoped to preview (Story 8).
- Pulse helper added to `highlightUtils.ts`; `clearHighlights` updated to drop per-comment highlights.

## Backlog (post-v1, not built now)
- Changing a comment's color **after** creation (explicitly an edge case below — defaults to backlog unless trivially free in the picker).
- Persisting the live `Range` across sessions (offsets) for resilient anchoring — current text-search re-find is the v1 mechanism.
- Filtering/sorting the panel by color.
- Comment threads / replies.
- Overlapping-highlight blend rendering (v1 uses last-writer-wins layering; see edge case).
- Color-coded "Send to Agent" grouping in the agent prompt.

---

## Out of Scope (with rationale)
- **Editing source from preview to "fix" a stale anchor** — preview is read-only for comment anchoring; the Edit tab already owns source editing. Mixing anchor-repair into preview violates single-responsibility and balloons the component past the 150-line limit.
- **Persisting `index`** — index is purely a function of document order over unresolved comments; persisting it would create drift bugs the moment a comment is added, resolved, or deleted. Derive it, never store it.
- **Cross-session range persistence** — out of MVP because the existing `findAnchorRange` text-search already locates anchors after reload without storing fragile offsets; adding offset persistence is a separate resilience effort (backlog).
- **More than 5 colors / custom hex** — fixed 5-preset palette keeps WCAG AA validation tractable (see accessibility) and keeps the picker simple.
- **Inline-style positioning for gutter/highlights** — forbidden by Studio rules; all dynamic positioning uses CSS custom properties set imperatively.

## Edge Cases & Risks
> Anchoring mechanism (critical): submitted/comment highlights are re-derived **every render** from the stored `lineText` string via `findAnchorRange` — there is no persisted Range for submitted comments. Most edge cases below resolve to "the text search either re-finds the anchor or returns null." The product rule is: **a comment whose anchor can't be found must never crash, must stay in the panel, and must visibly signal it is unanchored.**

- **Markdown content changes after a comment is submitted (text still present elsewhere):** highlight re-derives via `findAnchorRange` on the new content and re-anchors to the first match. Acceptable for v1. Risk: it may re-anchor to a *different* occurrence of the same text; accepted, documented limitation.
- **Anchor text is deleted from the file:** `findAnchorRange` returns `null`. Required behavior: no highlight, no gutter marker, no scroll target; the `CommentCard` shows an **"unanchored / orphaned"** visual state and remains in the panel (so the comment is never silently lost). Clicking it or keyboard-nav- landing on it is a no-op (Stories 5 & 8 skip it). It must still be sendable to the agent (its `lineText` carries the original context).
- **Two comments on overlapping (or identical) text:** each gets its own `pathly-comment-{id}` highlight. The CSS Custom Highlight API layers by registration order — the later-registered highlight's color wins in the overlap region (last-writer-wins). v1 does not blend colors. Both cards, both indices, and both gutter markers still render distinctly (gutter markers may visually stack — they must remain individually clickable). True blend rendering is backlog.
- **Comment color changed after submit:** color editing post-creation is **backlog**, not MVP. If the picker makes it trivially free to expose an edit affordance, then changing color must (a) re-persist `color`, and (b) update the highlight, card badge, and gutter marker on the next render — no reload required. Default decision: ship read-only color in v1.
- **Panel closed / not mounted when scroll-to is triggered:** `onScrollToComment` is owned by `CommentablePreview`, which is only mounted in the `preview` tab. If the trigger source isn't visible, the call is a safe no-op. If a future toggle can collapse the panel while preview stays mounted, scroll-to must still work (it targets the preview, not the panel). No crash in any case.
- **Rapid resolve/add churn:** indices re-derive each render (Story 9), and the sidecar persist is debounced 400ms (existing). Highlights/gutter must reconcile to the latest comment list, not a stale snapshot — drive them off the same `comments` array the panel uses.
- **Pulse overlap:** if a second scroll-to fires within the 300ms pulse window, the prior pulse must be cancelled/cleared before the new one starts (single active pulse).
- **Keyboard shortcut collision:** Alt+↑/↓ must not fire while focus is in the Edit textarea or the comment modal, and must not interfere with the global Ctrl/Cmd+S handler in `Editor/index.tsx`.

## Color Accessibility (WCAG AA — hard requirement)
All 5 preset colors must remain legible against **both** Studio light and dark backgrounds. The highlight is a background tint behind body text, so the binding constraint is **text-on-highlight contrast**, plus a secondary check that the highlight is distinguishable from the page background.

Acceptance criteria:
- For each of the 5 colors, in **both** themes, body text rendered over the highlight tint meets **WCAG AA**: ≥ 4.5:1 for normal text, ≥ 3:1 for large text (≥18.66px/24px or 14px bold).
- The index badge (number on color chip) meets ≥ 4.5:1 for its label text against the chip.
- Gutter markers (number on color chip) meet the same ≥ 4.5:1.
- The five colors are distinguishable from each other and from the page background at ≥ 3:1 boundary contrast (non-text UI contrast, WCAG 1.4.11), so adjacent/overlapping highlights remain separable.
- Color is **never the sole carrier of meaning** (WCAG 1.4.1): the index number on card, highlight-adjacent gutter, and panel ordering all convey identity independently of hue — covers color-vision deficiency.
- Highlight tints are defined as theme-aware CSS custom properties (one set per theme in `tokens.css`), not hardcoded hex in the component — so light/dark each get an independently AA-verified value.
- Verification gate: the chosen 10 values (5 colors × 2 themes) are checked with a contrast calculator before merge; failing values are darkened/lightened until they pass. This check is part of the story's Definition of Done, not optional polish.

## Open Questions
- OPEN: Is post-creation color editing wanted in v1, or firmly backlog? (Default assumed: backlog — read-only color in v1.)
- OPEN: For overlapping highlights, is last-writer-wins layering acceptable for v1, or is a striped/blended treatment expected? (Default assumed: last-writer-wins acceptable.)
- OPEN: Gutter marker placement when the preview has its own scroll container vs. the window — confirm which element scrolls so markers can be absolutely positioned against the correct offset parent.
- OPEN: Should keyboard nav (Alt+↑/↓) cycle resolved comments too, or unresolved only? (Default assumed: unresolved only, matching highlights/gutter.)
- OPEN: Exact pulse visual (color/opacity ramp) — architect/designer to specify; PO requires only that it is ≤300ms, single-active, and self-clearing.
- OPEN: When an anchor re-finds a *different* occurrence after content change, is silent re-anchoring acceptable, or should the card flag "anchor moved"? (Default assumed: silent for v1.)
