# PO Notes — studio-design-polish
_Generated by PO advisor (auto-flow)_

## Problem & Users
Pathly Studio's current UI has accumulated small but compounding design debt — undersized typography, inconsistent focus states, hardcoded borders, missing motion, and weak active states — that makes the desktop IDE feel less polished than the workflows it edits. Primary users are pipeline authors and operators who spend long sessions inside Studio configuring flows; secondary users include reviewers and new developers onboarding to the tool. The pain is friction: readability strain, lost keyboard focus, unclear navigation, and a generally "unfinished" feel that erodes trust in a tool meant to be a serious IDE.

## MVP Scope

### Story 1 — Readable Typography Baseline
**As a** pipeline author working long Studio sessions
**I want** a larger, modern base font (Inter at 15–16px)
**So that** I can read flow labels, form fields, and panel text without eye strain.
- Bump base font size from 13–14px to 15–16px across the app
- Replace system font stack with Inter (with system fallback)
- Verify line-height and spacing scale appropriately

### Story 2 — Consistent Keyboard Focus
**As a** keyboard-driven user
**I want** every interactive control (Button, Input, IconButton) to share the same visible focus ring
**So that** I always know where my focus is and never get lost tabbing through forms.
- Define a single focus-ring token in theme.ts
- Apply consistently to Button, Input, IconButton (and any other focusable primitives)
- Ensure the ring is visible in both light and dark themes

### Story 3 — Semantic Border Token
**As a** developer maintaining Studio's UI
**I want** a `--border` semantic token in the theme
**So that** borders are consistent across components instead of hardcoded one-off values.
- Add `--border` (and variants if needed: subtle, strong) to theme.ts
- Replace hardcoded border colors in existing components with the token

### Story 4 — Motion on Interactive Elements
**As a** Studio user
**I want** subtle 150ms ease-out transitions on snap state changes, hover, and active states
**So that** the UI feels responsive and alive rather than jumpy.
- Standardize a motion token (duration: 150ms, easing: ease-out)
- Apply to buttons, sidebar items, snap state changes, and other interactive transitions
- Respect `prefers-reduced-motion`

### Story 5 — Stronger Sidebar Active State
**As a** user navigating between Studio sections
**I want** the active sidebar item to be clearly highlighted
**So that** I always know which section I'm in at a glance.
- Strengthen the active-state visual treatment (background, accent bar, or weight change)
- Maintain accessible contrast in both themes

### Story 6 — FlowWizard Inline Validation & Progress
**As a** user filling out the multi-step FlowWizard
**I want** inline validation on each field and a visible step progress indicator
**So that** I know what's wrong before clicking Next and how far I am through the flow.
- Add inline validation messages tied to each form field
- Add a step progress indicator (e.g., "Step 2 of 4" with progress visual) at the top of the wizard
- Disable/enable Next based on current step validity

### Story 7 — Light Theme Contrast Compliance
**As a** user on the light theme (including users with low vision)
**I want** secondary text to meet WCAG AA contrast (4.5:1)
**So that** I can read all content comfortably and the product is accessible.
- Audit light-theme secondary text colors
- Adjust tokens until all body and secondary text passes 4.5:1
- Verify dark theme remains compliant after any shared-token changes

## Out of Scope
- Full visual redesign or rebranding (color palette overhaul, new logo, new iconography system)
- Restructuring component APIs or refactoring component logic beyond what's needed for tokens/styles
- New features in FlowWizard beyond validation + progress (e.g., no new steps, no new field types)
- Mobile/responsive layout work — Studio remains desktop-first
- Theming system extensions (new themes, user-customizable themes)
- Accessibility work beyond contrast and focus rings (e.g., full screen-reader audit is a separate effort)

## Success Criteria
- Base font size is 15–16px and Inter is loaded and applied across Studio
- All Button, Input, IconButton instances share one focus-ring style, verified by keyboard tabbing through main screens
- `--border` token exists in theme.ts and replaces hardcoded borders in at least the components touched
- Interactive elements animate at 150ms ease-out; `prefers-reduced-motion` disables transitions
- Sidebar active item is unambiguously distinguishable from inactive items in both themes
- FlowWizard shows inline validation on invalid fields and a step progress indicator; Next is gated on validity
- Light-theme secondary text passes WCAG AA 4.5:1 contrast (verified via automated check or manual audit)
- No regressions in dark theme contrast or existing component behavior

## Constraints
- Electron + React 18 + TypeScript stack — no framework changes
- Must support both light and dark themes
- Inter font must be bundled or loaded in a way that works offline (Electron desktop context)
- Changes should be token-driven where possible to keep future theming work cheap
- Respect `prefers-reduced-motion` OS setting
- No breaking changes to component public APIs consumed elsewhere in Studio

## Edge Cases & Risks
- Font swap to Inter may shift layout — components with fixed widths/heights may need spot fixes
- Increasing base font size may cause overflow or truncation in dense panels (sidebar, property inspectors)
- Hardcoded border replacements may surface inconsistencies (some "borders" may actually be shadows or dividers)
- Motion added to snap state changes could feel sluggish if applied to high-frequency updates — needs judgment per case
- Stronger sidebar active state could clash with existing accent color usage elsewhere
- Light-theme contrast fixes may force palette shifts that ripple into other components
