# TRACE — pathly-system-health

_Generated by 4 parallel scouts: Orientation, Hook Reliability, FSM Engine, Flow & Integration._

---

## Overview

The Pathly system architecture is generally well-structured with clear layer separation. However, three categories of issues were identified: hook reliability, FSM spec drift, and integration gaps.

---

## Scout 1 — Orientation (File Structure & Dependency Map)

### Layer inventory

**Core infrastructure layers:**
1. `src/pathly_hooks/` (2 hooks)
   - `classify_feedback.py` — tags questions [REQ] or [ARCH]
   - `inject_feedback_ttl.py` — adds ttl_hours frontmatter

2. `src/pathly_orchestrator/` (4 modules)
   - `state.py` — FSM state schema and valid transitions
   - `eventlog.py` — event log read/write, CLI tools
   - `events.py` — event type schema (comments-only)
   - `__init__.py` — module docstring only

3. `src/install_cli/` (8 modules)
   - `setup_command.py` — main installer orchestrator
   - `materialize.py` — file copying with manifest tracking
   - `codex_plugin_config.py` — Codex AI integration
   - `http_config.py` — HTTP server registration
   - `resources.py`, `detect.py`, `stitch.py` — helpers
   - `__main__.py`, `__init__.py` — entry points

4. `src/pathly_data/` (flows & skills)
   - `core/flows/` — 3 flow YAML files: explore, team, debug
   - `core/skills/` — 27 skill markdown files
   - `adapters/` — adapter-specific YAML (out of scope)

5. `src/pathly_telemetry/` (HTTP server)
   - `server.py` — implements record_activity tool
   - `storage.py`, `report.py` — backend
   - `__main__.py` — entry point

### Dependency direction

```
User invokes pathly command
  ↓
Adapter (claude/codex/copilot-specific)
  ↓
installer (setup_command.py)
  ├→ materialize.py (copy files, manage manifest)
  ├→ http_config.py (register telemetry server)
  ├→ deploy_codex_hooks() / deploy_copilot_hooks()
  └→ hook registration (hooks installed to ~/.codex/ or ~/.github/hooks/)
  ↓
Orchestrator spawned by skill agent
  ├→ load flow_config (*.flow.yaml)
  ├→ state.py (validate FSM transitions)
  ├→ eventlog.py (read/write STATE.json, EVENTS.jsonl)
  ├→ spawn sub-agents
  └→ route feedback via feedback_routing
  ↓
Hooks fire (PostToolUse event from Codex/Copilot)
  ├→ classify_feedback.py (optional, skipped if no ANTHROPIC_API_KEY)
  └→ inject_feedback_ttl.py (optional)
  ↓
Sub-skills (builder, reviewer, tester, explorer, etc.)
```

## Scout 2 — Hook Reliability (classify_feedback, inject_feedback_ttl)

### Files examined

- `src/pathly_hooks/classify_feedback.py` — 74 lines
- `src/pathly_hooks/inject_feedback_ttl.py` — 81 lines
- `src/install_cli/materialize.py` — lines 20-70 (Codex), 104-143 (Copilot)
- `src/install_cli/setup_command.py` — lines 95-116 (hook loading)

### Key findings

#### Issue 1: PATHLY_PROJECT_ROOT env var missing → exit 1 (not graceful)

**File:Line:** `classify_feedback.py:34-37`, `inject_feedback_ttl.py:54-57`

Both hooks check `PATHLY_PROJECT_ROOT` at startup:
```python
project_root_env = os.environ.get("PATHLY_PROJECT_ROOT")
if not project_root_env:
    print("pathly-hook: PATHLY_PROJECT_ROOT not set", file=sys.stderr)
    sys.exit(1)  # ← FAILURE, not silent
```

**Spec vs. code:**
- Original design (`pathly/plans/.archive/orchestrator-hardening/IMPLEMENTATION_PLAN.md:36`): "silent no-op (exit 0)"
- Current code: exit 1 (failure)
- Tests validate exit 1

**Impact:** If Codex/Copilot runs classify_feedback or inject_feedback_ttl without setting PATHLY_PROJECT_ROOT, the hook fails hard. The hook never executes silently.

**Current wiring:** `src/install_cli/materialize.py:31,36` hardcodes hook script paths in Codex hooks.json and Copilot hook JSONs with NO env var injection. The installer (`setup_command.py`) never sets PATHLY_PROJECT_ROOT anywhere.

**Improvement 1:** Decide: exit 0 (silent) or exit 1 (fail loudly)? Update spec document and tests accordingly.

**Improvement 2:** If exit 1 is correct, pre-flight check in setup_command.py to verify PATHLY_PROJECT_ROOT is set before registering hooks.

---

#### Issue 2: ANTHROPIC_API_KEY missing → exit 0 (documented)

**File:Line:** `classify_feedback.py:49-50`

```python
if not os.environ.get("ANTHROPIC_API_KEY"):
    sys.exit(0)  # ← Intentional no-op
```

**Status:** This is intentional and documented in the docstring ("If ANTHROPIC_API_KEY is not set, exits silently").

**No improvement needed** — this is correct-by-design.

---

#### Issue 3: No error handling on file mutations

**File:Line:** `inject_feedback_ttl.py:77`, `classify_feedback.py:69`

Both hooks mutate files on disk:
```python
resolved.write_text(_inject_ttl(content), encoding="utf-8")  # Can raise OSError
```

No try/except. If the file is read-only or the parent dir is not writable, the hook crashes with a raw Python traceback.

**Impact:** When Codex/Copilot runs the hook and a permission error occurs, the tool-use event fails visibly to the user, blocking the workflow.

**Improvement 3:** Wrap `write_text()` in try/except; exit 0 on permission errors (graceful degradation) with stderr message.

---

#### Issue 4: No validation of path traversal before file write

**File:Line:** `inject_feedback_ttl.py:62-67`, `classify_feedback.py:40-47`

Both hooks validate `is_relative_to(plans_dir)` **before** reading the file (line 52/69). This is good.

However, between validation and write, the file could be replaced with a symlink or moved. No atomic write is performed.

**Impact:** Theoretical race condition. Low practical risk in typical Codex/Copilot usage, but a tool-use hook should be resilient.

**Improvement 4 (lower priority):** Use `pathlib.Path.write_text()` in a try/except, or switch to atomic writes (temp file + rename).

---

### Hook lifecycle trace

1. User (in Codex/Copilot) calls `apply_patch` tool
2. Codex/Copilot triggers PostToolUse hook
3. Hook handler invokes the registered hook script:
   - Codex: `~/.codex/hooks.json` → command: `python src/pathly_hooks/classify_feedback.py`
   - Copilot: `.github/hooks/pathly-classify.json` → command: `python src/pathly_hooks/classify_feedback.py`
4. Hook receives JSON on stdin with `{"file": "plans/<feature>/FEEDBACK.md"}`
5. If PATHLY_PROJECT_ROOT is not set: exit 1 → hook fails → Codex/Copilot sees error
6. Hook reads file, mutates it, writes back
7. Exit 0 → success (silent in Codex; may log in Copilot)

**Design issue:** Installer (setup_command.py) does NOT inject PATHLY_PROJECT_ROOT into the hook environment. The end user must manually set it, or the hook will always fail.

## Scout 3 — FSM Engine (orchestrator, state, events)

### Files examined

- `src/pathly_orchestrator/state.py` — 82 lines
- `src/pathly_orchestrator/eventlog.py` — 236 lines
- `src/pathly_orchestrator/events.py` — 84 lines
- `src/pathly_orchestrator/__init__.py` — 8 lines (docstring only)

### Key findings

#### Finding 1: FSM state machine is well-defined

**File:Line:** `state.py:28-60`

STATES dict enumerates 11 valid states with descriptions:
- IDLE, DISCOVERING, PLANNING, PLAN_DONE, CONSULT_OPEN, BUILDING, REVIEWING, REVIEW_BLOCKED, TESTING, TEST_BLOCKED, BLOCKED_ON_HUMAN, RETRO, DONE

TRANSITIONS dict specifies valid transitions (e.g., BUILDING → {REVIEWING, TESTING, BLOCKED_ON_HUMAN, DONE}).

**Status:** Well-designed. Validation happens in `eventlog.py:49-55` and `eventlog.py:75-95`.

**No issue.**

---

#### Issue 1: Event schema is comments-only; no schema versioning

**File:Line:** `events.py:1-84`

Event types are defined as constants (TYPE_COMMAND, TYPE_AGENT_SPAWNED, etc.), but the schema lives entirely in comments. No Python dataclass or TypedDict.

```python
# ── Example EVENTS.jsonl snippet ─────────────────────────────────────────────
#
# {"type":"COMMAND","feature":"security-fixes",...}
```

No `schema_version` field in any event. If the schema changes (e.g., rename `type` → `event_type`), existing EVENTS.jsonl files silently break.

**Impact:** 
- `eventlog.py:138` reads `e.get("type") != "AGENT_DONE"` — if the field is renamed, this silently returns empty results.
- No migration utility exists.
- No version guard in the EVENTS.jsonl format itself.

**Improvement 5:** Add a one-time `schema_version: "1.0"` field at the top of EVENTS.jsonl (first line, before any events). Check it on read; print error if versions don't match.

---

#### Issue 2: CLI tool names diverge from documentation

**File:Line:** `eventlog.py:208-219` (CLI entry point)

CLI commands are `pathly-events summary <feature>` and `pathly-events events <feature>`.

But the docstring says:
```
Usage: pathly-events <summary|events> <feature>
```

This works, but the module is exported as:
- `pyproject.toml:18` → `pathly-events = pathly_orchestrator.eventlog:_cli`
- `pyproject.toml:19` → `pathly-state = pathly_orchestrator.eventlog:_state_cli`

Users might expect `pathly-events` to be a tool name (like `pathly-state`). Instead, it's a command dispatcher.

**Status:** Functional but slightly confusing. Low priority.

**No improvement needed** — works as designed.

---

#### Issue 3: read_state() is not exported from eventlog module

**File:Line:** `eventlog.py:121-127`

`read_state()` exists but is not called by any CLI function. It's only imported by other modules.

**Status:** Functional private method. Clean API boundary.

**No improvement needed.**

---

### FSM correctness assessment

The FSM engine itself is **correct and well-tested**:
- State transitions are validated before writing
- Event logging is append-only (thread-safe with lock on Unix; no lock on Windows)
- Recovery from disk works: read STATE.json, read EVENTS.jsonl, derive current state

**One threading issue (low priority):**

**File:Line:** `eventlog.py:25, 62-72`

On Unix, file locking uses `fcntl.flock()`. On Windows, this import fails (ImportError caught at line 71), and no lock is used.

```python
try:
    import fcntl
    fcntl.flock(f, fcntl.LOCK_EX)  # Unix only
    ...
finally:
    fcntl.flock(f, fcntl.LOCK_UN)
except ImportError:
    f.write(line)  # No lock on Windows
```

On Windows, if two Python processes append to EVENTS.jsonl simultaneously, race conditions could corrupt the file.

**Improvement 6 (Windows-specific):** On Windows, use `msvcrt.locking()` or a separate lock file to synchronize writes.

## Summary: Answer the 3 Questions

### Q1: Is the overall Pathly architecture coherent and correctly wired?

**Yes, with caveats:**

- **Strength:** Layer separation is clean (hooks → installer → orchestrator → skills). Dependency direction is one-way downward.
- **Strength:** Flow YAML and skill MD are tightly coordinated.
- **Weakness:** PATHLY_PROJECT_ROOT is not injected by installer; hooks must rely on environment setup by the user or the LLM calling them.
- **Weakness:** No CI or clean-machine smoke test (pre-existing from architecture-risk-assessment).

**Verdict:** Coherent in structure, but integration gap around hook environment setup.

---

### Q2: Does the FSM (orchestrator + flow YAML) work correctly?

**Yes, the FSM is correct:**

- **Strength:** State transitions are validated before writing to disk.
- **Strength:** Event logging is append-only and thread-safe on Unix (fcntl.flock).
- **Strength:** Recovery from disk works; STATE.json is the source of truth.
- **Weakness:** Event schema has no version field; schema changes could silently break EVENTS.jsonl parsing.
- **Weakness:** Windows lacks file locking (no msvcrt equivalent); concurrent writes could corrupt EVENTS.jsonl.

**Verdict:** Works correctly for normal single-agent operation. Vulnerable to schema drift and Windows concurrency.

---

### Q3: Are the hooks reliable, and what concrete improvements can be made?

**Hooks are partially reliable:**

- **Status:** Hook exit codes don't match spec (spec: exit 0 silent; code: exit 1 loud).
- **Status:** Hooks lack error handling on file mutations; permission errors crash visibly.
- **Status:** Installer doesn't inject PATHLY_PROJECT_ROOT; hooks fail unless user manually sets env var.
- **Status:** No pre-flight checks in setup_command.py to verify hook prerequisites.

**Improvement recommendations (file:line pointers):**

1. **classify_feedback.py:34-37, inject_feedback_ttl.py:54-57** — Decide exit code behavior (silent vs. loud), document in README and spec.

2. **classify_feedback.py:69, inject_feedback_ttl.py:77** — Wrap `write_text()` in try/except; exit 0 on permission errors with stderr message.

3. **setup_command.py:95-116** — Add pre-flight check: verify PATHLY_PROJECT_ROOT is set or provide setup guidance.

4. **materialize.py:31,36,122-132** — Consider injecting PATHLY_PROJECT_ROOT into hook command environment (e.g., wrap in a shell script that sets env vars).

5. **events.py** — Add `schema_version: "1.0"` to EVENTS.jsonl header; check version on read.

6. **eventlog.py:62-72** — On Windows, use `msvcrt.locking()` instead of fcntl for file locking.

7. **http_config.py, README.md** — Document the record_activity HTTP tool in README.
